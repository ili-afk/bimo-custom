# Rust: стоит ли переписывать BIMO

Короткий ответ: **Rust не сделает BIMO быстрее. Он сделает его легче и надёжнее в развёртывании.
Но «быстрее» — нет, потому что Python не является узким местом.**

Ниже — не мнение, а замеры по коду `brenpoly/be-more-agent`.

---

## 1. Где на самом деле уходит время

Я разобрал `agent.py` и выписал все задержки. Смотри, что нашлось:

| Что | Строка | Задержка |
|---|---|---|
| `time.sleep(0.5)` перед записью | 696 | **0.5 с** |
| `sd.stop()` + `time.sleep(0.2)` | 718–719 | **0.2 с** |
| ожидание тишины `silence_duration = 1.5` | 700 | **1.5 с** |
| запуск `whisper.cpp` через `subprocess.run` | 777 | **0.5–2 с** (загрузка модели) |
| облачная/локальная LLM | — | 0.3–1.5 с |
| запуск `piper` через `subprocess.Popen` | 970 | 0.2–0.5 с |

**Итого: ~2.2 секунды — это просто `sleep` и запуск процессов. Не вычисления.**

Вот это и есть настоящая причина, почему BIMO отвечает через 4–6 секунд. Причём `sleep(0.5)` —
это просто «подождать, чтобы микрофон отпустило», а `silence_duration = 1.5` — «подождать полторы
секунды тишины, чтобы понять, что человек закончил».

Сколько из этого списка уберёт Rust? **Ноль.** Это не язык, это логика. Хоть на Rust, хоть на C,
хоть на ассемблере — `sleep(1.5)` останется `sleep(1.5)`.

---

## 2. Почему Python здесь не тормозит

Вся тяжёлая работа уже **не на Python**:

| Что делает | На чём реально работает |
|---|---|
| Кодовое слово | `openwakeword` → **ONNX Runtime (C++)** |
| Распознавание речи | `whisper.cpp` → **C++**, отдельный бинарник |
| Синтез голоса | `piper` → **C++**, отдельный бинарник |
| Мозг | `ollama` → **Go**, модель в нативном коде |
| Микрофон/динамик | `sounddevice` → **PortAudio (C)** |
| Числа | `numpy`/`scipy` → **BLAS/LAPACK (C/Fortran)** |

Python — это **клей**: 1081 строка, которые решают «что делать дальше» и передают данные между
этими движками. Клей не бывает узким местом. Узкое место — движки и сеть.

Реальный вклад Python в задержку: **единицы миллисекунд на цикл**, меньше 1% от общего времени.

---

## 3. Что Rust реально даст (и это не «скорость»)

| Параметр | Python сейчас | Rust | Выигрыш |
|---|---|---|---|
| Память (RSS) | ~120–200 МБ (интерпретатор + numpy + scipy + PIL + tkinter) | ~20–40 МБ | **~5×** |
| Холодный старт | 1.5–3 с (импорты) | ~50 мс | **~30×** |
| Задержка ответа | 4–6 с | 4–6 с | **0** |
| Установка на Pi | `pip install` тянет колёса под ARM, `scipy`/`onnxruntime` иногда собираются часами | один статический бинарник | **сильно лучше** |
| Стабильность 24/7 | утечки ссылок, GIL, `xruns` в аудио под нагрузкой | предсказуемо | лучше |
| Скорость разработки | правка → запуск мгновенно | `cargo build` 30 с – 2 мин **на Pi** | **Rust хуже в 10–100×** |

Вот честный итог: **Rust выигрывает в памяти, старте и развёртывании. В скорости ответа — ноль.**

---

## 4. Что придётся написать самому (и это главная проблема)

Экосистема Rust для такого проекта есть, но она **дырявая** — придётся собирать пазл:

| Нужно | В Rust есть? | Цена |
|---|---|---|
| Whisper ASR | ✅ `whisper-rs` | нормально |
| Piper TTS | ✅ `piper-rs` (`PiperEngine::new(...)`) | нормально |
| ONNX-инференс | ✅ `ort` | нормально, но сырой API |
| Аудио I/O | ✅ `cpal` | нормально |
| **Кодовое слово** | ❌ **готового нет** | надо взять `wakeword.onnx` и **самому** написать мел-спектрограмму, нарезку окон, порог — это несколько сотен строк DSP, где легко ошибиться и получить ложные срабатывания |
| **LLM-тулзы / function calling** | ❌ почти ничего | в Python это 5 строк, в Rust — `serde` + `reqwest` + свои структуры на каждый инструмент |
| **Лицо на экране** | ❌ `tkinter` нет | `egui`/`iced` — другой мир, переписывать с нуля |

Плюс то, о чём обычно молчат: **`cargo build` на Raspberry Pi 5 идёт минутами**. Ты будешь
менять одну строку и ждать. На Python ты за это время сделаешь десять попыток.

## 5. Три пути — и когда каждый оправдан

### Путь A. Python (то, что мы выбрали) — **правильно сейчас**
Потому что: 4 недели до первого работающего робота, а не 4 месяца. Оригинал уже на Python —
ты его читаешь, а не переписываешь. Все туториалы, все Issues, весь код автора — на Python.

### Путь B. Python + точечно Rust через PyO3 — **если упрёшься**
Оставляешь Python главным, а **один** горячий модуль пишешь на Rust и подключаешь как
питоновский пакет (`maturin`). Кандидат ровно один: **аудио-конвейер кодового слова**
(мел-спектрограмма + нарезка окон), если появятся `xruns` или дрожание звука.
Это профессиональный путь: 90% гибкости Python, 100% скорости там, где надо.

### Путь C. Полный Rust — **только при одном из условий**
- цель — **Pi Zero 2 W / 512 МБ**, где 150 МБ интерпретатора физически не влезают;
- нужно **устройство на тысячах экземпляров**, где важна установка одним бинарником;
- ты хочешь **выучить Rust** — и готов, что робот поедет на 3–6 месяцев позже.

Если ни одного из этих условий нет — полный Rust это **потеря времени без выигрыша в отзывчивости**.

## 6. Как реально ускорить BIMO (это даст в 50 раз больше, чем Rust)

По порядку выгоды. Всё — правки в Python, суммарно вечер работы:

1. **Убрать `time.sleep(0.5)` и `0.2`** перед записью (строки 696, 719). Зачем они — понятно
   (освободить микрофон), но 0.7 с на каждый запрос — грабёж. Достаточно `sd.stop()` и проверки,
   что поток закрылся. **−0.7 с**
2. **Заменить `silence_duration = 1.5` на VAD** (Silero VAD или `webrtcvad`). VAD ловит конец речи
   по спектру, а не по громкости, и срабатывает за 0.3–0.5 с. **−0.8…1.0 с**
3. **Держать `whisper.cpp` резидентно** (режим сервера, модель загружена один раз), а не
   `subprocess.run` на каждый запрос. **−0.5…1.5 с** — самый большой кусок
4. **Предгенерировать фразы TTS** («Слушаю», «Думаю», «Не понял») в `.wav` заранее. Тогда
   мгновенная реакция есть ещё до того, как модель ответила. Субъективно ускоряет сильнее всего.
5. **Стримить ответ LLM** в TTS по предложениям, а не ждать весь текст. Первое слово звучит
   через 0.5 с вместо 3 с.
6. **Квантовать модель** (`q4_K_M` вместо `q8`), взять модель меньше — если мозг локальный.

**Итог: 4–6 с → 1.5–2 с.** Rust во всём этом списке не участвует ни разу.

---

## 7. Вывод

- **Учить Rust сейчас — нет.** Это второй язык, он не решает ни одной твоей текущей задачи.
- **«Легче» — да, Rust даст 5× по памяти.** Но на Pi 5 с 8 ГБ это не проблема. Проблема была бы на Pi Zero.
- **«Быстрее» — нет.** Задержку создают `sleep`, запуск процессов и сеть. Переписывание языка их не трогает.
- **Правильный порядок:** сначала Python + пункты из §6. Если после этого что-то реально упрётся —
  точечно Rust через PyO3. Полный Rust — только под Pi Zero или под продукт.

Если однажды захочешь Rust — начни с него **не как с замены**, а как с отдельного демона
`bimo-audio` (слушает микрофон, отдаёт события по сокету). Тогда Python-мозг остаётся, а горячий
цикл уезжает в Rust. Это единственная схема, где Rust окупается.
